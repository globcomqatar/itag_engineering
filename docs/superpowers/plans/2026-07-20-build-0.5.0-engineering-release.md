# Build ITAG-0.5.0 — Engineering Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **This plan is greenfield** — unlike Builds 0.1.0-0.4.0, none of this build's DocTypes exist in the codebase yet, so field lists/workflow states/anchors below are a considered design, not a re-statement of verified existing schema. Every implementer task below still carries the same obligation established across Builds 0.1.0-0.4.0: verify assumptions against the LIVE bench (existing field names on Work Order, existing roles, existing DocTypes this build links to) before writing code — do not assume this plan's field lists are final if live verification contradicts them.

**Goal:** Implement formal Engineering Release — the mechanism that turns an approved engineering baseline (Item + Product Revision + Drawing Revision + BOM + Routing + Inspection Plan) into a production-usable, immutable, approval-gated release, and freeze that baseline onto every Work Order at submission. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 13.

**Architecture:** Two new standalone DocTypes (`Engineering Approval Matrix` — a reusable, priority-ordered rule-resolution config, shared with Build ITAG-0.6.0's ECO per roadmap §15.7; and `Engineering Release` — the transactional release record with a Workflow) plus 3 child tables (`Approval Step`, `Release Checklist`, `Release Distribution`) plus 1 link-collection child table (`Engineering Release Specification`, linking to Build 0.3.0's `Technical Specification`). One new service module (`release_service.py`) implements the multi-step transactional release boundary (§13.6) and the effective-release resolver (§13.7). Work Order baseline freeze (§13.8) is implemented via `hooks.py` `doc_events` on the core `Work Order` DocType — **this is the sanctioned Frappe extension mechanism, not a core-file modification**: `doc_events` handlers live entirely in this app's own Python files; core ERPNext files are never touched. This build also closes out a forward-reference left open by Build ITAG-0.4.0: `BOM.itag_engineering_release` and `Routing.itag_engineering_release` were `Data` placeholders (no such DocType existed yet) — Task 1 converts them to real `Link` fields now that `Engineering Release` exists.

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

- **Known bug classes from Builds 0.2.0-0.4.0 — every task below must actively guard against these, not just the ones a task explicitly calls out:**
  1. **Workflow-state / mirror-field desync** (hit Engineering Drawing and Product Revision in Build 0.3.0): if `release_status` is BOTH a workflow-state field AND something else reads/branches on it, sync must be unconditional and first in `validate()`. Prefer making `release_status` itself the one true workflow-state field (no separate mirror) if at all possible, to eliminate the whole bug class rather than re-fixing it a third time.
  2. **Permission checks on the API wrapper only, not the underlying service function** (hit `run_duplicate_check_api` in 0.2.0 and `evaluate_bom_readiness` in 0.4.0): every service function with a real side effect must gate permissions inside itself, not just its `@frappe.whitelist()` wrapper.
  3. **Child-table immutability gaps** (hit Product Revision in 0.3.0's final review): any "immutable once X" guard must explicitly walk `meta.get_table_fields()` and compare serialized child rows, not just `meta.get_valid_columns()` (which never includes Table fields).
  4. **Date/Datetime `!=` comparison bugs**: use `self.has_value_changed(fieldname)`, never manual `!=`, for any released/frozen-field comparison.
  5. **Naive positional list diffing** (hit BOM comparison in 0.4.0): any diff between two ordered lists of records (e.g. comparing two Engineering Releases' checklists, or two approval-step sequences) must use `difflib.SequenceMatcher` opcodes, not index-by-index comparison, if reordering/insertion/removal in the middle of the list is possible.
  6. **`frappe.db.set_value` on a derived/computed field bumping `modified` and causing spurious `TimestampMismatchError` for a concurrent editor** (hit `evaluate_bom_readiness` in 0.4.0's final review): any read-triggered or background-triggered write to a derived field (e.g. resolving/caching the effective release, refreshing approval-step status display) must pass `update_modified=False` unless the write is a genuine user-initiated state change.
  7. **Test-fixture collisions with pre-existing ERPNext demo data** (hit BOM tests in 0.4.0): use `itag_engineering/tests/factories.py`'s `create_fresh_stock_item(prefix)` for any new stock Item a test needs; never pick an arbitrary existing Item.
  8. **Missing idempotency guards on "create exactly one X" operations** (the roadmap explicitly requires this for the release transaction itself, §13.6 step 11, and it recurs in Build 0.9.0's successor Work Order service) — `submit_engineering_release()` must be safe to call twice on the same release without creating two supersession chains or double-firing notifications.

- Produces: `resolve_approval_disciplines(context: dict) -> dict` where `context` = `{"company": ..., "product_family": ..., "item_category": ..., "safety_classification": ..., "change_risk": ..., "cost_impact": ..., "is_customer_specific": bool, "is_regulatory": bool, "transaction_date": ...}`. Returns `{"matrix": <matched Engineering Approval Matrix name>, "disciplines": [{"sequence": ..., "discipline": ..., "required_role": ...}, ...], "requires_cost_review": bool, "requires_customer_review": bool}`. Raises `frappe.ValidationError` with a clear message when zero rules match ("No approval matrix rule matches this context — configuration required") or when more than one ACTIVE rule matches with the SAME priority and an equally-specific condition set (ambiguous — per roadmap §13.4 "The matrix shall resolve one unambiguous approval path"); when multiple rules match with DIFFERENT priorities, the lowest `priority` number wins (same tie-break convention as Item Code Rule).

**Specificity/ambiguity design note:** "equally specific" means: after filtering to only rules whose every non-blank condition field matches the context, if more than one surviving rule shares the SAME priority value, that's ambiguous and must raise. If priorities differ, the lower number wins outright regardless of how many conditions each specifies (a deliberate simplification of "most specific wins" — using explicit priority ordering, which the Item Code Rule precedent already established as this house's chosen mechanism, rather than inventing a specificity-scoring algorithm from scratch). Document this design choice in the service's own docstring so a future build doesn't "fix" it into something inconsistent.
