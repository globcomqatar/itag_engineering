# Build ITAG-0.10.0 — WIP and Traceability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Greenfield plan** — verify every assumption below against the LIVE bench before trusting it. Presumes Build ITAG-0.9.0 is complete and merged. **This build resolves the last outstanding forward-reference in the app** (`Rework Instruction.source_wip_unit`) and reuses an already-built policy model discovered during this plan's own research — see the Architecture note below, do not skip re-reading `itag_engineering/setup/custom_fields.py`'s existing Item fields before designing Task 1.

**Goal:** Provide engineering-aware WIP identity and complete forward/backward manufacturing traceability for valve production — from a raw-material heat/batch/serial all the way to a delivered finished valve, and back again. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 21.

**Architecture:** One new DocType (`WIP Unit Register`, with self-referential parent/child genealogy). Standard-field extensions (§21.3) on `Serial No`/`Batch`/`Quality Inspection`/`Stock Entry`/`Purchase Order`/`Purchase Receipt`/`Sales Order`/`Delivery Note`/`Work Order`/`Job Card` via `custom_fields.py` (the same core-doctype-extension mechanism already used for Work Order in Build 0.5.0 — no core file edits). **Important discovery from this build's own research: Build ITAG-0.2.0 already added `Item.itag_serial_tracking_required`/`itag_batch_tracking_required`/`itag_heat_tracking_required`/`itag_wip_unit_tracking_required` (confirm these 4 field names are still exactly this by re-reading `custom_fields.py`'s `get_custom_fields()` function before relying on them) — these ARE the roadmap's §21.5 "Traceability Identity Policy," already modeled 8 builds ago. This build's job is to USE these existing flags to decide when a WIP Unit Register entry is created and how traceability services behave per item, not to invent a new policy model.** Heat-number tracking (§21.2/§21.3) is modeled as a `Batch`/`Serial No` extension field (`itag_heat_number`, `itag_material_certificate`), not a separate DocType — matching Decision Log #6's framing of heat tracking as a property of existing batch/serial records, not an independent master.

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

## Global Constraints

- No ERPNext or Frappe core file may be modified. All extensions to `Serial No`/`Batch`/etc. are custom fields via `custom_fields.py`, exactly like every prior build's core-doctype extensions.
- **This build resolves the app's LAST forward-reference placeholder**: `Rework Instruction.source_wip_unit` converts `Data` → `Link` (options `WIP Unit Register`) in Task 1, via the same patch mechanism established in Builds 0.5.0/0.6.0/0.7.0. After Task 1, grep the whole `custom_fields.py` and every DocType JSON for the words "placeholder"/"forward reference" and confirm zero remain — this is the last one by design (every subsequent build only references DocTypes that already exist by the time it's built).
- Ruff config: 110-char lines, tabs, double quotes, `py310` target.
- All tests use `frappe.tests.utils.FrappeTestCase` (class-scoped rollback only).
- Site under test: `frappedevelopment.localhost`. Bench commands via:
  `docker exec -u frappe frappe-docker_devcontainer-frappe-1 bash -lc "cd /workspace/development/frappe-bench && <command>"`
- Work happens on git branch `build-0.10.0-wip-traceability` created from `develop`. Commit after each task.
- House convention (Decision Log #16): custom fields in `custom_fields.py`; single-level path `itag_engineering/itag_engineering_management/...`. No new Workflow (WIP Unit Register is a plain tracked-status record, not an approval chain).
- Company scope: single company (Decision Log #2) — resolve dynamically. Warehouse structure per Decision Log #10.
- **Known bug classes — actively guard against all of these**:
  1. Workflow-state / mirror-field desync — not applicable (no Workflow), but `quality_status`/`hold_status`/`rework_status`/`disposition_status` on WIP Unit Register are DERIVED from other documents (Quality Inspection, Production Engineering Hold, Rework Instruction, Material Disposition respectively) — these must be kept LIVE/re-queried or refreshed via a clear, single mechanism (e.g. a `refresh_wip_status(wip_unit_name)` service function called at specific trigger points), never hand-edited fields that can silently drift from the real source-of-truth documents they're supposed to reflect.
  2. Permission checks belong inside the service function itself, not only its `@frappe.whitelist()` wrapper — directly relevant here since `backward_traceability`/`forward_traceability` may expose customer-identifying information across company boundaries; roadmap §21.7 explicitly requires "Permission filters protect controlled customer and engineering information."
  3. Child-table immutability — not applicable to WIP Unit Register itself, but genealogy (`parent_assembly`/`child_components`) must never be silently rewritten once a component has been physically consumed into a parent assembly (a lighter, targeted guard — not a full "immutable once released" pattern — similar in spirit to Build 0.8.0's narrow "executed decision row" guard, not Build 0.3.0's whole-document pattern).
  4. `self.has_value_changed(fieldname)` for any Date/Datetime comparison.
  5. **Naive positional list/tree traversal — directly relevant here**: genealogy traversal (walking `child_components` recursively for backward traceability, or walking "what consumed this WIP Unit" forward) needs the SAME circular-reference guard pattern Build 0.4.0's `bom_traversal_service`/`bom_readiness_service` established (a `_visited` set passed through recursive calls) — a WIP Unit genealogy loop is physically impossible in reality but must still not hang the service if bad data ever creates one; reuse the exact established pattern, do not re-derive it.
  6. Any read/background-triggered `frappe.db.set_value` write to a derived field (e.g. `refresh_wip_status`'s writes) must pass `update_modified=False`.
  7. Use `create_fresh_stock_item()` from `factories.py` for any new stock Item a test needs.
  8. **Performance at representative scale** (§21.7 "Representative large traceability queries meet performance targets", §22.6 lists forward/backward traceability as something Build ITAG-0.11.0 will performance-harden) — this build should record a baseline timing measurement (same spirit as Build 0.7.0's own recorded-but-not-gated performance baseline) for a deep genealogy chain (at least 4 levels), for Build 0.11.0 to compare against, not invent a hard target of its own beyond what Decision Log #13 already established (small expected volume, no special scaling strategy anticipated).

**Interfaces (§21.4):**
- `backward_traceability(serial_or_wip_unit) -> dict` — resolves to a `WIP Unit Register`/`Serial No` if given the other, then walks: `original_work_order` → Job Cards/operations → `engineering_release` (via `release_service.retrieve_released_baseline`, Build 0.5.0 — **reuse, do not re-derive**) → product/drawing/BOM/routing/inspection revisions → recursively into `child_components` (genealogy, with the SAME `_visited`-set cycle guard as Build 0.4.0's BOM traversal — Global Constraint #5) → component serials/batches → linked `Purchase Receipt`/supplier (via Batch/Serial's originating Purchase Receipt, if ERPNext tracks this natively — confirm the real field path rather than assuming) → `Quality Inspection` records → `Deviation Request`/`Concession Approval`/`ECO`/`Rework Instruction` references found anywhere along the chain.
