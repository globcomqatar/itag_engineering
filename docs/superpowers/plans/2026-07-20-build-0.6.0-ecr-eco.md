# Build ITAG-0.6.0 — Engineering Change Request and Engineering Change Order Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Greenfield plan** — verify every assumption below (field names, role names, Frappe API behavior) against the LIVE bench before trusting it; this plan is a considered design against the roadmap and prior builds' precedent, not a restatement of already-built schema. Presumes Build ITAG-0.5.0 is complete and merged (branch off `develop` after that merge) — do not start this build before confirming `Engineering Release` and `Engineering Approval Matrix` actually exist on the target branch.

**Goal:** Implement the formal Engineering Change Request (ECR) and Engineering Change Order (ECO) lifecycle — from problem identification through an approved, fully-defined set of controlled engineering changes ready for impact analysis (Build ITAG-0.7.0) and implementation. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 15.

**Architecture:** Two new Workflow-driven DocTypes (`Engineering Change Request`, `Engineering Change Order`) plus 2 child tables (`ECR Affected Object`, `Controlled Change`). **Reuses Build 0.5.0's `Engineering Approval Matrix`/`resolve_approval_disciplines()` and `Approval Step` child doctype as-is** — the roadmap explicitly states "The ECO shall use Engineering Approval Matrix rules" (§15.7); do not build a second, parallel approval-resolution mechanism. Continues this app's established forward-reference pattern: `Engineering Change Order` needs to gate on a Change Impact Assessment that doesn't exist until Build ITAG-0.7.0, so this build adds a `Data` placeholder field (`change_impact_assessment`) and a plain `impact_analysis_status` Select — mirroring exactly how Build 0.4.0's `itag_applicable_eco` was a placeholder that Build 0.6.0 (this build) now finally resolves for BOM/Routing/Engineering Release (Task 1).

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

- Work happens on git branch `build-0.6.0-ecr-eco` created from `develop` (after Build 0.5.0 merges). Commit after each task.
- House convention (Decision Log #16): custom fields in `itag_engineering/setup/custom_fields.py`; Workflow fixtures in `itag_engineering/fixtures/workflow.json`, name added to the `fixtures` filter list in `hooks.py` (now 5 workflow names: EIR, Engineering Drawing, Product Revision, Engineering Release, and this build's 2 new ones — `Engineering Change Request Workflow`, `Engineering Change Order Workflow`). Single-level path `itag_engineering/itag_engineering_management/...`.
- Company scope: single company (Decision Log #2) — resolve dynamically, never hardcode.
- **Known bug classes — actively guard against all of these, not just task-specific call-outs** (carried forward from Builds 0.2.0-0.5.0's actual bug history):
  1. Workflow-state / mirror-field desync — make the workflow-state field itself the one true state field wherever possible (as Build 0.5.0 did for `release_status`); if a SEPARATE `implementation_status` or `impact_analysis_status` field must coexist alongside the workflow state (both this build's ECO genuinely needs, since they track orthogonal concerns, not the same state twice), confirm neither one is ever meant to mirror the other before assuming a sync guard is even needed.
  2. Permission checks belong inside the service function itself, not only its `@frappe.whitelist()` wrapper.
  3. Child-table immutability (if any "locked" state applies to ECR/ECO here — confirm against the roadmap: ECR/ECO do NOT have a released-baseline immutability requirement the way Drawing/Product Revision/Inspection Plan/Engineering Release do; a Closed ECR/ECO should still be protected from accidental edits via a simple `validate()` guard, but this is a much lighter requirement than the "immutable once Released" pattern — do not over-engineer a full child-table diff guard here unless the roadmap actually calls for one; it doesn't (§15.11's checkpoint list is about approval/workflow bypass, not field immutability)).
  4. `self.has_value_changed(fieldname)`, never manual `!=`, for any Date/Datetime comparison.
  5. Naive positional list diffing — not directly relevant to a new record type with no "compare two ECOs" requirement in this build's own scope, but if any report needs to diff `Controlled Change` rows against something, use `difflib.SequenceMatcher`.
  6. Any read/background-triggered `frappe.db.set_value` write to a derived field must pass `update_modified=False`.
  7. Use `create_fresh_stock_item()` from `factories.py` for any new stock Item a test needs.
  8. **Segregation of duties — this build is where the roadmap's own test checkpoint explicitly calls it out for the first time** ("Requestor cannot perform prohibited final approval", §15.11, and UAT-017 Unauthorized Approval, §15.11): the ECR Requestor's role must NOT appear in the resolved approval matrix's required roles for that same ECR's own ECO, OR if it legitimately does (e.g. an Engineering Manager both requests AND is a required approver by role), the SAME USER must not be allowed to satisfy two DIFFERENT required-discipline approval steps on the same document (reuse Build 0.5.0's `Approval Step` segregation check exactly, do not re-derive it from scratch).
  9. **Workflow transition reachable without calling the real service** (hit Build 0.2.0's EIR "Create Item" transition): `create_eco_from_accepted_ecr()` must be the ONLY path that creates an ECO from an ECR — if the ECR Workflow's "Accepted for ECO" transition is a bare `apply_workflow` state change with no server-side guard forcing the real service to have been called, an ECR could get stuck in "Accepted for ECO" with no ECO ever created (the exact bug class Build 0.2.0's final review fixed with a `validate()` guard). Add the equivalent guard here: `Engineering Change Request.validate()` blocks a transition INTO `"Accepted for ECO"` unless a real ECO already references this ECR as `source_ecr` (checked via `has_value_changed("workflow_state")`-gated logic, mirroring the exact fix from Build 0.2.0 commit `fba776b`).
