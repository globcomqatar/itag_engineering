# Build ITAG-0.8.0 — Engineering Hold and Material Disposition Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Greenfield plan** — verify every assumption below against the LIVE bench before trusting it. Presumes Build ITAG-0.7.0 is complete and merged. **This build back-fills the two domains Build 0.7.0's impact analysis explicitly deferred** (Engineering Hold, Deviation/Concession) — Task 7 wires the real DocTypes into `impact_analysis_service.py`'s two `"not_yet_implemented"` placeholder scan functions.

**Goal:** Block unsafe downstream production/inventory activity while an engineering change is pending disposition, and control exactly how affected stock/WIP is dispositioned (continue under old revision, use as-is, rework, return, alternate use, quarantine, consume under deviation, scrap, or await customer decision) through reconciled, auditable transactions. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 18.

**Architecture:** Four new DocTypes (`Production Engineering Hold`, `Material Disposition`, `Deviation Request`, `Concession Approval`) plus one child table (`Material Disposition Decision`). Hold ENFORCEMENT is implemented via `hooks.py` `doc_events` on core ERPNext doctypes whose actions the roadmap requires holds to be able to block (`Job Card`, `Stock Entry`, `Quality Inspection`, `Delivery Note`) — the same sanctioned "no core modification" extension mechanism Build 0.5.0 established for Work Order baseline freeze. Stock movement always goes through real ERPNext `Stock Entry` documents (never direct Stock Ledger Entry manipulation), per roadmap §18.8. **Deviation Request and Concession Approval both link to ERPNext's existing Quality Action module rather than duplicating an NCR workflow**, per Decision Log #11 — confirm Quality Action's real DocType/field names live before designing the link (do not assume a specific ERPNext version's Quality Action shape without checking `frappe.get_meta("Quality Action")` on this bench first).

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

## Global Constraints

- No ERPNext or Frappe core file may be modified. All hold enforcement is `doc_events` hooks; all stock movement is real `Stock Entry` documents.
- **This build backfills Build 0.7.0's two deferred impact-analysis domains** — do this LAST (Task 7), after the Hold and Disposition DocTypes are real and stable, mirroring exactly how Build 0.6.0's Task 1 and Build 0.7.0's Task 1 each closed out the PRECEDING build's forward-reference deferral. After Task 7, `impact_analysis_service.py`'s `scan_engineering_hold_stock`/`scan_deviations_and_concessions` must return real data, not the `{"status": "not_yet_implemented", ...}` placeholder — confirm by re-running Build 0.7.0's `unresolved_impact_exceptions` report against a fresh analysis and confirming those two domains no longer appear in it.
- Ruff config: 110-char lines, tabs, double quotes, `py310` target.
- All tests use `frappe.tests.utils.FrappeTestCase` (class-scoped rollback only).
- Site under test: `frappedevelopment.localhost`. Bench commands via:
  `docker exec -u frappe frappe-docker_devcontainer-frappe-1 bash -lc "cd /workspace/development/frappe-bench && <command>"`
- Work happens on git branch `build-0.8.0-engineering-hold-disposition` created from `develop`. Commit after each task.
- House convention (Decision Log #16): custom fields in `custom_fields.py`; single-level path `itag_engineering/itag_engineering_management/...`. This build introduces no new Workflow (Hold/Disposition/Deviation/Concession are plain Select-status documents with service-enforced transitions, not Frappe Workflow-driven — the roadmap's own test checkpoint language here is about BLOCKING actions and RECONCILING quantities, not about a multi-role approval chain of the kind Engineering Release/ECO have; confirm this reading is correct by re-checking §18.3-§18.7 for any workflow-shaped language before assuming, since getting this wrong would mean skipping a genuinely-needed Workflow fixture).
- Company scope: single company (Decision Log #2) — resolve dynamically. Warehouse structure per Decision Log #10 (Raw Material, WIP, Finished Goods, Quarantine/Engineering Hold, Rework, Scrap) — confirm these warehouses actually exist on the site (they may not, if Decision Log #10 was only ever a decision on paper, not yet provisioned) before writing tests that assume them; create them in a test factory if missing, matching this app's established "resolve dynamically, create if needed" convention.
- **Known bug classes — actively guard against all of these**:
  1. Workflow-state / mirror-field desync — not directly applicable (no Workflow here), but `Production Engineering Hold.status` (Active/Released) and `Material Disposition.status` (Draft/Submitted/Reconciled/Executing/Complete) are each a SINGLE source of truth in their own document — do not let any report or service cache a "derived" copy of either status anywhere else that could drift.
  2. Permission checks belong inside the service function itself, not only its `@frappe.whitelist()` wrapper — especially critical here since `hold_service.py`'s blocking checks run inside OTHER doctypes' `doc_events` (Job Card/Stock Entry/etc.) where there is no natural "wrapper" layer at all; the block-check function itself must be safe to call from any context.
  3. Child-table immutability — `Material Disposition Decision` rows should NOT be freely editable once a row's `execution_status == "Executed"` (a real Stock Entry has already moved real stock against it) — add a narrow, row-level guard for this specific case (not a whole-document "immutable once released" pattern like Engineering Drawing; just: an executed decision row's `quantity`/`decision_type` cannot change after execution).
  4. `self.has_value_changed(fieldname)` for any Date/Datetime comparison — directly relevant to Deviation/Concession expiry checking (`validity_to` vs. today).
  5. Naive positional list diffing — not directly relevant to new documents in this build, but if any report compares two dispositions' decision rows, use the established `difflib` pattern.
  6. Any read/background-triggered `frappe.db.set_value` write to a derived field must pass `update_modified=False` (e.g. if a scheduled job auto-expires a Deviation Request when `validity_to` passes, that status flip is a background write, not a user edit).
  7. Use `create_fresh_stock_item()` from `factories.py` for any new stock Item a test needs.
  8. **Quantity reconciliation precision** (§18.6, explicitly in the roadmap's own test checkpoint "Disposition quantities reconcile"): floating-point sums must use an explicit tolerance (e.g. `abs(total - assessed) < 0.0001`), never exact `==` comparison on floats — confirm ERPNext's own precision-handling convention (`flt()`, `frappe.utils.flt` with a `precision` argument) and reuse it rather than a bespoke epsilon.
  9. **Duplicate execution prevention** (§18.10 test checkpoint "Duplicate disposition execution is blocked", explicitly the same *shape* of bug this app has hit before in different guises — Build 0.6.0's idempotent ECO creation, Build 0.7.0's idempotent job restart): `execute_disposition_decision()` must check `execution_status != "Executed"` before creating a Stock Entry, and the check-then-act must be safe under the same kind of double-click/concurrent-call race the earlier idempotency guards were built to survive (consider locking the parent `Material Disposition` document, e.g. `frappe.get_doc(...).lock()` or a `select ... for update` pattern, if a plain re-check proves insufficient under a live concurrent-call test).
  10. **Expired/exhausted/out-of-scope Deviation or Concession must be rejected at USE time, not only flagged at a glance** (§18.7 "Expired, exhausted, or out-of-scope approvals shall be blocked", and UAT-013): whatever consumes a Deviation/Concession reference (a Material Disposition Decision with `decision_type="Consume Under Approved Deviation"`) must call a real validation function against the CURRENT date/remaining quantity/customer-or-project scope at the moment of use, not trust a `status` field that might be stale.
