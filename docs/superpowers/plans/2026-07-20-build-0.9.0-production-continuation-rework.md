# Build ITAG-0.9.0 — Production Continuation and Rework Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Greenfield plan** — verify every assumption below against the LIVE bench before trusting it. Presumes Build ITAG-0.8.0 is complete and merged.

> ## ⚠️ MANDATORY ENTRY GATE — DO NOT START THIS BUILD WITHOUT THIS
>
> Roadmap §17 ("Mandatory Entry Condition") and §19.2 both require: **"The selected ERPNext-version manufacturing prototype must be completed and approved before `ITAG-0.9.0` development begins."** As of this plan being written, `doc/ITAG_Decisions.md` Decision Log #8 explicitly lists the prototype as **"Still Open"** — it records stated operating practice only, not prototype-verified behavior. **Before dispatching Task 1 of this build, confirm with the user that the manufacturing prototype (roadmap §7.4: multi-op Work Order, Job Card partial completion, material transfer, successor Work Order, stock/costing/traceability preservation, all demonstrated end-to-end against the real v15.117.0 ERPNext install using vanilla ERPNext — no `itag_engineering` code required) has actually been run and its findings recorded as an update to Decision Log #8.** If it has not, this build's entire design (especially Task 3's Successor Work Order Service and Task 5's Job Card Compatibility Service) is at risk of being built against assumed rather than verified ERPNext behavior — the roadmap treats this as a hard gate for exactly that reason. This plan's task designs below are written assuming the prototype's findings will CONFIRM Decision Log #8's stated mixed-model behavior (both material-transfer modes, both completion behaviors supported); if the prototype finds ERPNext v15.117.0 actually behaves differently, this plan's Task 3/5 designs must be revised before implementation, not adapted ad hoc mid-task.

**Goal:** Create a controlled process for completing acceptable old-revision production, stopping the remainder, reusing existing accepted components, generating exactly one successor Work Order under the new engineering baseline, and reworking affected WIP — without losing production history or double-counting completed work. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 19.

**Architecture:** Two new DocTypes (`Production Change Continuation`, `Rework Instruction`) plus 2 child tables (`Rework Operation`, `Rework Material`). Version-specific Work Order/Job Card behavior is isolated in the ALREADY-EXISTING `itag_engineering/itag_engineering_management/compatibility.py` (present in the codebase since an earlier build — **read its current contents first, do not assume it's empty or write a competing module**; Decision Log #1 references "the compatibility-service pattern the roadmap already specifies" as the intended home for exactly this kind of version-specific logic). The Successor Work Order Service reuses Build 0.5.0's `resolve_effective_release()`/`work_order_baseline.py` (a successor Work Order is just another new Work Order submitted against a new release — the SAME baseline-freeze hook fires automatically, no new freeze logic needed) and Build 0.8.0's `disposition_service.py` (confirming accepted/reworked/scrapped/returned quantities via already-executed Material Disposition Decisions, not by re-deriving quantity state from scratch).

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

## Global Constraints

- No ERPNext or Frappe core file may be modified. All version-specific Work Order/Job Card handling lives in `compatibility.py`.
- **Forward-reference**: `Rework Instruction.source_wip_unit` must be a `Data` placeholder, not a Link — the `WIP Unit Register` DocType doesn't exist until Build ITAG-0.10.0. This is the SAME established pattern as every prior forward-reference in this app; Build ITAG-0.10.0's own plan is responsible for converting it once that DocType exists (add an explicit Task 1-style conversion patch to that build's plan, matching Builds 0.5.0/0.6.0/0.7.0's precedent — cross-reference this obligation when writing that plan).
- Ruff config: 110-char lines, tabs, double quotes, `py310` target.
- All tests use `frappe.tests.utils.FrappeTestCase` (class-scoped rollback only).
- Site under test: `frappedevelopment.localhost`. Bench commands via:
  `docker exec -u frappe frappe-docker_devcontainer-frappe-1 bash -lc "cd /workspace/development/frappe-bench && <command>"`
- Work happens on git branch `build-0.9.0-production-continuation-rework` created from `develop`. Commit after each task.
- House convention (Decision Log #16): custom fields in `custom_fields.py`; single-level path `itag_engineering/itag_engineering_management/...`. No new Workflow in this build (Production Change Continuation and Rework Instruction are service-driven status documents, not multi-role approval chains — confirm this reading against §19.4/§19.7 before assuming, since `approval_status` fields exist on both and a genuinely multi-step approval chain would need a real Workflow rather than a plain Select).
- Company scope: single company (Decision Log #2) — resolve dynamically.
- **Known bug classes — actively guard against all of these**:
  1. Workflow-state / mirror-field desync — not directly applicable (no Workflow here), but `Production Change Continuation` has FIVE separate status-shaped fields (`material_return_status`, `material_reuse_status`, `approval_status`, `execution_status`, `reconciliation_status`) that must each remain genuinely independent, not silently expected to move in lockstep — confirm each is actually orthogonal before assuming a sync guard between any pair is unnecessary.
  2. Permission checks belong inside the service function itself, not only its `@frappe.whitelist()` wrapper.
  3. Child-table immutability — not applicable; these are working documents, not released/frozen baselines.
  4. `self.has_value_changed(fieldname)` for any Date/Datetime comparison.
  5. Naive positional list diffing — not directly relevant here, but if `Original-to-Successor Work Order Reconciliation` (Task 6's report) ever compares two Work Orders' operation lists, use the established `difflib` pattern rather than index-by-index.
  6. Any read/background-triggered `frappe.db.set_value` write to a derived field (e.g. `remaining_production_quantity` recomputation) must pass `update_modified=False`.
  7. Use `create_fresh_stock_item()` from `factories.py` for any new stock Item a test needs.
  8. **"Create exactly one successor Work Order" idempotency** (§19.6 step 13, and explicitly UAT-020 "Idempotent Successor Creation") is THE central correctness risk in this build, structurally identical in shape to Build 0.6.0's idempotent ECO-from-ECR creation and Build 0.8.0's idempotent disposition execution — reuse the SAME idempotency-key-plus-existing-reference-check pattern established in both of those, do not invent a third variant.
  9. **No double-counting of completed finished goods or reusable sub-assemblies** (§19.5's own explicit warning: "shall not double-count completed finished goods or reusable sub-assemblies") — this is a NEW risk class specific to this build, not previously seen: the quantity formula subtracts BOTH `completed_acceptable_quantity` AND `existing_accepted_component_quantity` from the original planned quantity, and it is easy for a buggy implementation to subtract a quantity twice if a completed finished good is ALSO counted as a reusable component elsewhere (e.g., a completed sub-assembly that is itself both "accepted completed production" from the ORIGINAL Work Order's perspective and "an existing accepted component" from a DIFFERENT Work Order's perspective). Every task touching quantity calculation must include an explicit test scenario proving no such double-count occurs, not just a happy-path arithmetic test.
