# Build ITAG-0.11.0 — Security, Audit, Performance, and Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Greenfield plan** — verify every assumption below against the LIVE bench before trusting it. Presumes Build ITAG-0.9.0/0.10.0 are complete and merged (this build hardens the whole app built across Builds 0.1.0-0.10.0; it does not depend on new business DocTypes of its own beyond the two small ones listed below).

> ## ⚠️ OPEN DECISION REQUIRED BEFORE TASK 6 (MIGRATION) — DO NOT ASSUME A SOURCE SYSTEM
>
> Roadmap §22.7 lists what MAY migrate (existing engineering Items, drawings, BOMs, etc.) but neither the roadmap nor `doc/ITAG_Decisions.md` identifies **what the actual source system or format is** — a legacy ERPNext instance, a spreadsheet register, paper records, or something else. Decision Log #12 (Active-only migration) records the RETENTION policy, not the SOURCE. **This is a genuinely open decision, not yet made** — per this app's established discipline of never building a permanent assumption for an unresolved material decision (roadmap Appendix D), Task 6 below must not be started until a new Decision Log entry records the actual source system/format. Tasks 1-5, 7 of this build do not depend on this and can proceed regardless.

**Goal:** Harden the complete application for production use — permissions, segregation of duties, audit trail, observability, and performance — and build the controlled data-migration toolkit. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 22. This is the last build before final certification (`ITAG-1.0.0`); its own exit gate (§22.12) explicitly requires re-running EVERY UAT scenario from every prior build.

**Architecture:** Two new lightweight DocTypes: `Engineering Audit Log` (append-only, a thin wrapper around what many builds' service functions already do implicitly via Frappe's own `track_changes`/Version mechanism, made explicit and queryable for the specific event list §22.4 requires) and `Migration Batch` (+ `Migration Exception` child table, Task 6 only). A new role, `ITAG Integration User`, models the roadmap's explicit "Integration users cannot approve or release engineering records" requirement (§22.3) — this role exists SPECIFICALLY to be denied every approval/release permission every other role in this app has been granted since Build 0.2.0, proving the negative case rather than only the positive ones. **No new business logic DocTypes beyond these two** — this build is almost entirely: (a) a permission/segregation-of-duties TEST SUITE across everything built so far, (b) `audit_service.py` calls added into MANY already-existing service files (a mechanical, wide-reaching but low-risk-per-line change), (c) performance measurement/indexing against the SAME operations already measured/flagged in Builds 0.4.0/0.7.0/0.10.0, and (d) the migration toolkit (Task 6, gated per the box above).

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

## Global Constraints

- No ERPNext or Frappe core file may be modified. Observability reuses Frappe's own `RQ Job`/`Error Log`/`Integration Request` doctypes wherever they already cover the roadmap's ask — do not build parallel tracking mechanisms for things Frappe already tracks; report ON them instead.
- Ruff config: 110-char lines, tabs, double quotes, `py310` target.
- All tests use `frappe.tests.utils.FrappeTestCase` (class-scoped rollback only).
- Site under test: `frappedevelopment.localhost`. Bench commands via:
  `docker exec -u frappe frappe-docker_devcontainer-frappe-1 bash -lc "cd /workspace/development/frappe-bench && <command>"`
- Work happens on git branch `build-0.11.0-security-audit-performance-migration` created from `develop`. Commit after each task.
- House convention (Decision Log #16): custom fields in `custom_fields.py`; single-level path `itag_engineering/itag_engineering_management/...`. No new Workflow.
- Company scope: single company (Decision Log #2) — the "Company and facility filtering" requirement (§22.2) is consequently mostly a no-op FOR NOW (nothing to filter between), but the permission-query-condition mechanism should still be built correctly (scoped to the single company) so it requires no redesign if Decision Log #2 is ever revisited for multi-company (explicitly listed in roadmap §34 as a post-1.0 future capability) — do not hardcode "ITAG International Company" inside the condition logic itself; read it from `Engineering Settings` (Build 0.1.0's Single DocType) the same way every other build has resolved company dynamically.
- **Known bug classes — actively guard against all of these, this build especially, since it is explicitly the "go back and check everything" build**:
  1. Workflow-state / mirror-field desync — re-audit EVERY workflow-bearing DocType built so far (Engineering Item Request, Engineering Drawing, Product Revision, Engineering Release, Engineering Change Request, Engineering Change Order) as part of Task 1's security review, specifically re-confirming no NEW code added in Builds 0.5.0-0.10.0 introduced a mirror-field desync of the kind already fixed 3 times in Builds 0.2.0-0.3.0.
  2. Permission checks inside the service function itself — Task 1's audit should specifically grep every `@frappe.whitelist()` function across the whole app and confirm each one's underlying bare function ALSO gates permissions (the exact recurring gap Builds 0.2.0/0.4.0 each found and fixed once) — this is a natural, comprehensive sweep for this build to do that no single prior build was scoped to do completely.
  3. Child-table immutability — re-confirm live (not just by reading code) that every "immutable once Released/Executed" guard built across Builds 0.3.0/0.4.0/0.5.0/0.8.0/0.10.0 still holds after all the intervening builds' changes; a regression here would be exactly the kind of thing only a full-app final hardening pass would catch.
  4. `self.has_value_changed(fieldname)` — same full-sweep confirmation for any Date/Datetime comparison across the app.
  5. Naive positional list diffing — confirm every comparison/diff function built so far (BOM comparison, drawing comparison, product revision comparison) still uses `difflib.SequenceMatcher` and none has regressed to positional comparison.
  6. `update_modified=False` on derived-field writes — audit every `frappe.db.set_value` call across the whole app (not just the ones already fixed) and confirm none of them bumps `modified` on a document a concurrent interactive user might have open, per the exact class of bug Build 0.4.0's final review found in `bom_readiness_service.py`.
  7. Use `create_fresh_stock_item()` for test items — confirm no build has silently reverted to an arbitrary-Item pattern.
  8. **This build's own new risk**: adding `audit_service.py` calls into many existing service functions (Task 3) must not change any of those functions' EXISTING behavior or performance characteristics in a way that breaks their existing tests — each file touched in Task 3 must have its existing test suite re-run and confirmed still green immediately after the edit, not batched until the end.
