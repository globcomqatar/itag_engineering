# Build ITAG-0.7.0 — Change Impact Analysis Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. **Greenfield plan** — verify every assumption below against the LIVE bench before trusting it. Presumes Build ITAG-0.6.0 is complete and merged (branch off `develop` after that merge).

**Goal:** Automatically identify every production, inventory, procurement, quality, customer, and delivered-unit record an approved or proposed engineering change (ECO) affects, as a background-processed, staleness-aware assessment. Per `ITAG_Engineering_Management_Master_Roadmap_v1.0(Approved).md` Section 16. This build closes the LAST forward-reference placeholder in the app (`Engineering Change Order.change_impact_assessment`, left as `Data` by Build ITAG-0.6.0) and makes the ECO workflow's "Impact Analysis Required" gate real for the first time.

**Architecture:** One new DocType (`Change Impact Assessment`, no Workflow of its own — `analysis_status` is a plain background-job-driven Select, matching this app's established distinction between workflow-driven approval documents and plain computed-status documents like Build 0.4.0's BOM `itag_release_readiness_status`). One background-job service (`impact_analysis_service.py`) built almost entirely on REUSE of existing services rather than new domain logic: Build 0.4.0's `bom_traversal_service.find_where_used()`/`get_multi_level_bom_tree()` for the BOM/component-expansion domain, and direct ERPNext core reads (`frappe.get_all` against `Work Order`, `Job Card`, `Stock Entry`, `Purchase Order`, `Purchase Receipt`, `Sales Order`, `Delivery Note`, `Serial No`, `Batch`, `Quality Inspection`) for every other domain — **read-only queries against core ERPNext doctypes, which is not a core modification** (no core file is edited; this is the same category of extension as any ERPNext report). Uses Frappe's standard background-job queue (`frappe.enqueue`) rather than inventing a custom job runner.

**Tech Stack:** Frappe v15.115.0 / ERPNext v15.117.0, MariaDB, ruff (flit_core), FrappeTestCase.

## Global Constraints

- No ERPNext or Frappe core file may be modified. All domain scanning is read-only `frappe.get_all`/`frappe.db.get_value` queries against core doctypes — never writes.
- **This build resolves the ECO forward-reference placeholder**: `Engineering Change Order.change_impact_assessment` converts `Data` → `Link` (options `Change Impact Assessment`) in Task 1, via the same patch mechanism Builds 0.5.0/0.6.0 established. **After this task, the app has zero remaining `Data`-typed forward-reference placeholders** — confirm this explicitly (grep the whole `custom_fields.py` for the word "placeholder" or "forward reference" in field descriptions and confirm every match has now been resolved by this build or an earlier one).
- **This build makes the ECO workflow's "Impact Analysis Required" → "Discipline Review" transition condition-gated for real**, per Build 0.6.0's own explicit deferral: Task 1 also patches `Engineering Change Order Workflow`'s transition (in `itag_engineering/fixtures/workflow.json`) to add `"condition": "doc.impact_analysis_status == 'Complete'"` (confirm the exact Frappe Workflow condition-expression syntax against `frappe/model/workflow.py` before writing it, matching the same verification Build 0.5.0 Task 4 already did for its own conditional transitions — do not assume the syntax is identical to a Python `if` without checking). A stale assessment (`staleness_status == "Stale"`) must ALSO block this transition — confirm whether Frappe Workflow conditions support boolean `and` between two doc-attribute checks in one string, or whether two field checks need to be combined into one derived boolean field on the ECO (e.g. `impact_analysis_ready_for_review` Check, computed by `validate()`) that the condition then checks — pick whichever is simpler and confirm it live rather than assuming.
- Ruff config: 110-char lines, tabs, double quotes, `py310` target.
- All tests use `frappe.tests.utils.FrappeTestCase` (class-scoped rollback only).
- Site under test: `frappedevelopment.localhost`. Bench commands via:
  `docker exec -u frappe frappe-docker_devcontainer-frappe-1 bash -lc "cd /workspace/development/frappe-bench && <command>"`
- Work happens on git branch `build-0.7.0-change-impact-analysis` created from `develop`. Commit after each task.
- House convention (Decision Log #16): custom fields in `custom_fields.py`; single-level path `itag_engineering/itag_engineering_management/...`. This build introduces no new Workflow of its own (only patches the existing ECO workflow's condition), so no new entry is needed in `hooks.py`'s `fixtures` filter list beyond what's already there — confirm this is really true before skipping that step.
- Company scope: single company (Decision Log #2) — resolve dynamically.
- **Known bug classes — actively guard against all of these**:
  1. Workflow-state / mirror-field desync — `analysis_status` and `staleness_status` are two genuinely orthogonal concerns here (one tracks job lifecycle, the other tracks input-freshness), not a mirror pair; do not conflate them into a sync-guard problem that doesn't actually exist.
  2. Permission checks belong inside the service function itself. This build introduces its FIRST genuinely background-executed (non-interactive-user-triggered) write path (`frappe.enqueue`'d analysis job) — confirm the enqueued job function itself does NOT need the same interactive-user permission gate as the function that QUEUES it (the queueing API call is what needs the permission check; the background job runs as whatever user Frappe's job runner executes as — confirm this live, since getting this wrong either blocks legitimate background execution or accidentally lets an unprivileged user's queued job run with elevated effective permissions).
  3. Child-table immutability — not applicable to this build; a Change Impact Assessment is a computed report, not a released/frozen baseline document.
  4. `self.has_value_changed(fieldname)` for any Date/Datetime comparison — relevant here for staleness detection's "relevant transaction state changes after the accepted cutoff" check, which is fundamentally a datetime comparison; do not use manual `!=`/`<` on possibly-mixed str/datetime values without normalizing first (the exact bug class that hit Build 0.3.0 twice).
  5. **Naive positional list diffing — directly relevant here**: if any part of staleness detection compares "the set of Work Orders scanned at analysis time" vs. "the set of Work Orders that exist now" to detect new/removed relevant transactions, use SET operations (`set(a) - set(b)`) or `difflib.SequenceMatcher` as appropriate — never assume the two lists are in the same order.
  6. Any read/background-triggered `frappe.db.set_value` write to a derived field (e.g. `progress`, `analysis_status` updates during a running background job) must pass `update_modified=False` — this build's background job writes to the SAME assessment document repeatedly as it progresses, which is exactly the "report/background write causing a spurious `TimestampMismatchError` for a concurrent editor" bug class Build 0.4.0's final review found and fixed; do not reintroduce it here in a new form. If a user has the assessment form open while the background job is updating its own progress, that update must not corrupt the user's next save.
  7. Use `create_fresh_stock_item()` from `factories.py` for any new stock Item a test needs — and this build's tests will build somewhat deep multi-level BOM trees (reusing Build 0.4.0's `get_multi_level_bom_tree` test patterns) which is exactly where the historical collision bug hit hardest; be doubly careful here.
  8. **Duplicate-job prevention** (roadmap §16.4, and explicitly listed in §16.7's Unit tests): queueing a second analysis for the same ECO while one is already `Queued`/`Running` must be blocked or return the existing job's reference, not silently start a second concurrent analysis of the same ECO.
  9. **Idempotent restart** (§16.4): if a background job fails/is killed mid-run and re-enqueued for the same `analysis_version`, re-running it must produce the same result, not accumulate duplicate impact-result rows from the partial prior run. Since this design stores results as one JSON blob per assessment (overwritten wholesale on each run, never appended-to), this should be structurally satisfied — confirm with a live test that force-fails a job partway and re-runs it, rather than assuming the design is safe without checking.

### Task 3: Impact analysis background-job service

**Files:**
- Create: `itag_engineering/itag_engineering_management/impact_analysis_service.py`
- Create: `itag_engineering/itag_engineering_management/test_impact_analysis_service.py`

**Interfaces (§16.2-§16.4):**
- `enqueue_impact_analysis(eco_name) -> str` — **the permission-gated, user-facing entry point** (per Global Constraint #2's note on where the gate belongs). Checks no `Queued`/`Running` assessment already exists for this `eco_name` (Global Constraint #8's duplicate-job prevention); creates a new `Change Impact Assessment` doc (`analysis_status="Queued"`, computes `input_checksum`); calls `frappe.enqueue("itag_engineering.itag_engineering_management.impact_analysis_service.run_impact_analysis", assessment_name=..., queue="long", timeout=...)` (confirm the right queue name/timeout convention by checking `common_site_config.json`/how other long-running Frappe background jobs in this bench are enqueued, rather than guessing a value); returns the new assessment's name immediately (does not block on completion).
- `run_impact_analysis(assessment_name)` — **the actual background-job function** (not directly permission-gated the same way, per Global Constraint #2 — runs under whatever identity Frappe's job runner uses; confirm this live). Sets `analysis_status="Running"`, `started_at=now`, `update_modified=False` on every intermediate write (Global Constraint #6); iterates the impact domains (§16.3), writing into `impact_results[domain_name]`, updating `progress` after each domain; wraps the whole run in try/except so a domain-scan failure sets `analysis_status="Failed"` + `error_status=<message>` rather than leaving the job silently stuck at `"Running"` forever (§16.4 "Failure capture"); on success sets `analysis_status="Complete"`, `completed_at=now`, computes `summary_counts` from `impact_results`, and notifies the user who triggered it (`frappe.publish_realtime`/a notification log entry, matching the lightweight notification approach already used in Builds 0.5.0/0.6.0).
- **Domain scan functions** (one per §16.3 domain, each returning a JSON-serializable list/dict, called by `run_impact_analysis`):
  - `scan_bom_where_used(eco)` — reuses Build 0.4.0's `bom_traversal_service.find_where_used(item_code)` for every Item referenced by the ECO's `controlled_changes` rows whose `reference_doctype == "Item"` or `"BOM"` (resolve the Item's own code if the reference is a BOM). **Do not re-derive where-used logic — call the existing function.**
  - `scan_open_work_orders(item_codes)` — `frappe.get_all("Work Order", filters={"production_item": ["in", item_codes], "status": ["not in", ("Completed", "Stopped", "Closed")]}, ...)` (confirm the real status values via `frappe.get_meta("Work Order").get_field("status").options` before assuming).

  - `scan_material_transferred_and_consumed(work_order_names)` — via `Stock Entry` rows linked to the affected Work Orders (`purpose in ("Material Transfer for Manufacture", "Manufacture")`).
  - `scan_wip_stock(item_codes)` — current stock in WIP-designated warehouses (per Decision Log #10's warehouse structure — "WIP" warehouse name).
  - `scan_completed_subassemblies` / `scan_finished_stock` — via `Stock Ledger Entry`/`Bin` for the affected items and their parent assemblies (from the where-used tree).
  - `scan_engineering_hold_stock` — **this domain has NO backing DocType until Build ITAG-0.8.0** (Production Engineering Hold doesn't exist yet); this scan function must be a documented no-op / "Not Yet Available" placeholder result for this build, returning an explicit `{"status": "not_yet_implemented", "note": "Engineering Hold is Build ITAG-0.8.0's scope"}` rather than silently returning an empty list that looks like "confirmed no holds exist" — this distinction matters for `unresolved_impact_exceptions` (Task 5) not to under-report.
  - `scan_open_purchase_orders` / `scan_open_purchase_receipts` / `scan_supplier_material` — via `Purchase Order Item`/`Purchase Receipt Item` filtered by affected item codes.
  - `scan_sales_orders` / `scan_customer_projects` / `scan_delivery_notes` — via `Sales Order Item`/`Delivery Note Item` filtered by affected item codes.
